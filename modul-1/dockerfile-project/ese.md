## 1. Чому я обрав Dockerfile

Програмісти часто кажуть «у мене працює». Програма запускається на ноутбуці розробника, а на сервері чи в колеги падає. Причина зазвичай не в самому коді, а в середовищі: інша версія Python, бракує системної бібліотеки, інша змінна оточення. Dockerfile придумали саме для цієї проблеми. Мені цікаво, що тут мова описує не *алгоритм*, а *середовище*. Це добрий приклад предметної мови (DSL): вона вміє робити одну річ і нічого більше.

## 2. Яку задачу розвʼязує Dockerfile і хто ним користується

**Dockerfile** — це текстовий файл з інструкціями. За ним Docker збирає **образ** (image): «знімок» файлової системи, у якому вже є операційна система (зазвичай урізаний Linux), потрібні бібліотеки, код програми та команда запуску. З образу запускають **контейнер**. Це ізольований процес, який на будь-якій машині з Docker бачить те саме середовище.

Задача, яку розвʼязує мова: **описати відтворювано, коротко й декларативно, як із нуля отримати середовище, готове до запуску програми.**

Хто ним користується:

- **Розробники.** Вони пишуть Dockerfile для свого сервісу, щоб будь-хто з команди міг запустити проєкт однією командою.
- **DevOps-інженери та адміністратори.** Вони збирають з образів серверну інфраструктуру, CI/CD-конвеєри, Kubernetes-кластери.
- **Тестувальники та студенти.** Вони отримують готове середовище без ручного встановлення десятка залежностей.

Кінцевий «споживач» Dockerfile — не людина, а **програма `docker build`**. Проте читають файл люди, тому він має бути зрозумілим для обох.

## 3. Мінімальний робочий приклад

Візьмімо маленький вебсервіс на Python (Flask), який повертає «Привіт» за адресою `/`.

**app.py**
```python
from flask import Flask

app = Flask(__name__)

@app.route("/")
def hello():
    return "Привіт з контейнера!"

if __name__ == "__main__":
    app.run(host="0.0.0.0", port=5000)
```

**requirements.txt**
```
flask==3.0.3
```

**Dockerfile**
```dockerfile
# 1. Базовий образ: урізаний Debian з уже встановленим Python 3.12
FROM python:3.12-slim

# 2. Робоча тека всередині образу (створиться, якщо її немає)
WORKDIR /app

# 3. Спершу копіюємо ЛИШЕ список залежностей
COPY requirements.txt .

# 4. Встановлюємо залежності (окремий шар, кешується)
RUN pip install --no-cache-dir -r requirements.txt

# 5. Тепер копіюємо решту коду
COPY . .

# 6. Документуємо, який порт слухає програма
EXPOSE 5000

# 7. Команда, яка виконується під час запуску контейнера
CMD ["python", "app.py"]
```

**Як зібрати й запустити:**
```bash
docker build -t hello-app .
docker run -p 5000:5000 hello-app
```
Далі відкриваємо `http://localhost:5000` і бачимо «Привіт з контейнера!».

### Пояснення рядок за рядком

| Рядок | Що відбувається |
|---|---|
| `FROM python:3.12-slim` | Кожен Dockerfile починається з `FROM`. Ми не ставимо Linux і Python самі, а беремо готовий офіційний образ. Тег `3.12-slim` фіксує версію Python і «легку» збірку без зайвих пакетів. |
| `WORKDIR /app` | Аналог `mkdir -p /app && cd /app`. Усі наступні команди виконуються в цій теці. |
| `COPY requirements.txt .` | Копіює файл з моєї машини (контексту збирання) в `/app` всередині образу. Крапка означає «поточна робоча тека», тобто `/app`. |
| `RUN pip install ...` | Виконує команду **під час збирання** образу. Результат (встановлені пакети) зберігається в образі. `--no-cache-dir` не залишає кеш pip, тож образ менший. |
| `COPY . .` | Копіює весь проєкт. Що копіювати не треба (наприклад `.git`, `venv`), вказують у файлі `.dockerignore`. |
| `EXPOSE 5000` | Лише документація: «програма слухає порт 5000». Порт насправді відкривається прапорцем `-p` у `docker run`. |
| `CMD ["python", "app.py"]` | Виконується **під час запуску** контейнера, а не під час збирання. Це головна різниця між `RUN` і `CMD`. |

Важливо розуміти: **кожна інструкція створює окремий шар** (layer) образу. Шари складаються один на одного, як прозорі плівки, і кешуються. Цей механізм і є основою вдалого рішення з наступного розділу.

## 4. Вдале рішення в синтаксисі: послідовність інструкцій = шари з кешем

Синтаксис Dockerfile — це просто список інструкцій зверху вниз. Немає циклів, функцій чи умов. Здається, що це бідність мови. Насправді це її сила.

Оскільки кожен рядок — це шар, Docker під час повторного збирання перевіряє: «чи змінилася ця інструкція і файли, які вона використовує?» Якщо ні, він бере шар з кешу. Щойно щось змінилося, перезбираються цей шар і **всі наступні**.

Звідси порядок у моєму прикладі:

```dockerfile
COPY requirements.txt .                              # змінюється рідко
RUN pip install --no-cache-dir -r requirements.txt   # довго, але кешується
COPY . .                                             # змінюється постійно
```

Коли я правлю `app.py`, змінюється лише останній `COPY`. Встановлення залежностей (найдовший крок) береться з кешу, і збирання триває секунди, а не хвилини.

Якби я написав навпаки:
```dockerfile
COPY . .
RUN pip install -r requirements.txt
```
то будь-яка зміна коду перевстановлювала б усі бібліотеки.

Чому це вдало саме як **рішення мови**:

- Мені не треба окремо описувати, що кешувати. Структура файлу *сама є* описом кешу. Лінійний синтаксис збігається з тим, як система працює всередині.
- Файл читається як рецепт: «візьми основу → підготуй теку → постав залежності → поклади код → запусти». Людина, яка ніколи не бачила Docker, приблизно зрозуміє, що відбувається.
- Відсутність умов і циклів робить збирання **передбачуваним**: той самий Dockerfile дає той самий результат.

Подібну ідею має і **багатоетапне збирання** (multi-stage build): кілька `FROM` в одному файлі. На першому етапі компілюємо програму з усіма інструментами, на другому копіюємо в чистий маленький образ лише готовий результат (`COPY --from=build ...`). Це той самий лінійний синтаксис, без нових складних конструкцій.

## 5. Невдале рішення в синтаксисі: дві форми запису `CMD` / `ENTRYPOINT` / `RUN`

Інструкції `CMD`, `ENTRYPOINT` і `RUN` можна записати двома способами:

```dockerfile
# exec-форма (JSON-масив)
CMD ["python", "app.py"]

# shell-форма (звичайний рядок)
CMD python app.py
```

Виглядають майже однаково, але поводяться по-різному:

1. **Shell-форма** насправді запускає `/bin/sh -c "python app.py"`. Головним процесом контейнера (PID 1) стає оболонка `sh`, а не Python. Коли виконуємо `docker stop`, сигнал `SIGTERM` отримує `sh` і, як правило, **не передає його** програмі. Програма не може коректно завершитися (зберегти дані, закрити зʼєднання). Docker чекає 10 секунд і вбиває її через `SIGKILL`.
2. **Exec-форма** запускає `python` напряму, і сигнали доходять. Але в ній **не працюють** підстановки змінних на кшталт `$PORT`, бо немає оболонки, яка б їх розкрила.
3. Exec-форма — це JSON, тому **лапки мають бути подвійні**. Рядок
   ```dockerfile
   CMD ['python', 'app.py']
   ```
   не є коректним JSON. Docker не видає помилку, а *мовчки* вважає це shell-формою і намагається виконати команду `['python',` — контейнер падає з незрозумілою помилкою.

Чому це невдало:

- **Дві форми для однієї дії** з різною поведінкою, і різниця не видна з першого погляду.
- **Помилка не виявляється під час збирання.** Мова «пробачає» неправильний синтаксис і змінює зміст замість того, щоб відмовитися збиратися.
- Новачкові доводиться знати про PID 1, сигнали Unix і JSON, щоб правильно написати *одну команду запуску*. Межа предметної мови «протікає»: мова мала б сховати ці деталі, а вона їх показує.

Краще було б мати одну форму або хоча б суворе правило: неправильний масив — помилка збирання.

## 6. Як це робилося б без Dockerfile і чому було б гірше

Без Dockerfile є кілька способів підготувати середовище.

**а) Інструкція в README.**
«Встановіть Python 3.12, виконайте `pip install -r requirements.txt`, встановіть `libpq-dev`...» Це текст для людини, а не для машини. Його ніхто автоматично не перевіряє, він застаріває, і на Windows, macOS та різних версіях Linux кроки відрізняються. Саме звідси береться «у мене працює».

**б) Shell-скрипт `setup.sh`.**
Скрипт автоматизує кроки, але змінює **саму машину**: ставить пакети в систему, може зламати інші проєкти з іншими версіями бібліотек. Повторний запуск може дати інший результат (уже щось встановлено, `apt` підтягнув нову версію). Немає ізоляції, кешу кроків і способу «відкотитися».

**в) Звичайна мова програмування (Python, Bash, Go).**
Можна написати програму, яка створює теку, копіює файли, ставить залежності й запускає процес в ізоляції через механізми ядра Linux (namespaces, cgroups). Але тоді:
- треба самому реалізувати кешування кроків, шари, передачу образу на іншу машину;
- кожна команда винайшла б свій формат, і чужий проєкт довелося б вивчати з нуля;
- у мові загального призначення є цикли, умови, мережа. Збирання може залежати від чого завгодно, тож результат стає менш передбачуваним.

Dockerfile робить навпаки: **обмежує можливості**, щоб отримати відтворюваність, кешування й єдиний формат, який розуміють усі інструменти (Docker, Podman, Kubernetes, GitHub Actions, GitLab CI).

**г) Віртуальна машина (наприклад, Vagrant).**
Ізоляція є, але кожна ВМ містить повну операційну систему: гігабайти диска, хвилини на запуск, багато памʼяті. Контейнер використовує ядро хоста, важить десятки-сотні мегабайтів і стартує за секунду.

Підсумок: без Dockerfile задачу розвʼязати можна, але це буде або *неавтоматизовано* (README), або *неізольовано* (скрипт), або *занадто важко* (своя програма, ВМ). Предметна мова дає оптимальну точку посередині.

## 7. Межі мови: де Dockerfile перестає допомагати

Розуміти, чого мова **не вміє**, так само важливо:

- **Один Dockerfile = один образ.** Якщо сервісів кілька (вебзастосунок + база даних + Redis), Dockerfile не описує, як їх запустити разом і зʼєднати. Для цього є інша предметна мова — `docker-compose.yml` (на основі YAML), а у великих системах — маніфести Kubernetes.
- **Немає повноцінної логіки.** Немає `if`, циклів, функцій. Є лише `ARG` для параметрів збирання. Якщо потрібно щось складне (наприклад, різна поведінка для різних середовищ), логіку виносять у shell-скрипт, який викликається через `RUN` або `ENTRYPOINT`, або в окремий конвеєр CI.
- **Не відповідає за дані.** Контейнер «одноразовий»: все, що записано всередині, зникає після видалення. Для постійних даних потрібні томи (volumes), які налаштовують поза Dockerfile.
- **Не гарантує повної відтворюваності сам по собі.** `RUN apt-get install curl` сьогодні й через рік поставить різні версії. Щоб цього уникати, фіксують версії пакетів і базового образу (`python:3.12-slim`, а краще — за digest `@sha256:...`).
- **Секрети.** Якщо записати пароль у `ENV` чи скопіювати файл з ключем, він назавжди лишиться в шарі образу. Для цього потрібні окремі механізми (`--secret` у BuildKit, змінні під час запуску).

Отже, упершись у межу, я б не намагався «викрутити» Dockerfile, а взяв би наступний інструмент: Compose для кількох сервісів, скрипт для логіки, CI для різних середовищ.

## 8. Висновок

Dockerfile — гарний приклад предметної мови. У ньому лише близько півтора десятка інструкцій, немає змінних у звичному сенсі, циклів чи функцій, але він розвʼязує одну важливу задачу: **однаково й відтворювано підготувати середовище для програми на будь-якій машині**. Найсильніша ідея мови — збіг синтаксису з внутрішнім механізмом: рядок = шар = одиниця кешу. Найслабше місце — дві форми запису команд, які мовчки поводяться по-різному. Мова загального призначення тут була б гіршою не тому, що вона «не може», а тому, що може *забагато*, а саме обмеження дає Dockerfile передбачуваність.
